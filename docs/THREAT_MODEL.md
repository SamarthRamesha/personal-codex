# Threat review — 2026-11-07

Trust boundaries: the owner controls the native client and authenticated backend; repositories, model output, conversation text and memory content are untrusted data. A single owner principal currently has access to registered projects. Tailscale connectivity alone confers no API authority.

| Threat | Implemented control | Residual / next action |
| --- | --- | --- |
| Malicious repository / prompt injection | Explicitly untrusted bounded context, closed JSON tool schemas, per-round digest approvals; model prose cannot authorize tools or completion. | Tests execute repository code under the host account. Do not run untrusted repositories until OS-level isolation and egress enforcement are implemented and verified. |
| Malicious tool descriptions / provider output | Fixed local tool vocabulary, unknown fields rejected, bounded streams, terminal-marker validation, exact hashes and test evidence. | Provider-native tool calls are not implemented; capability metadata now states this accurately. |
| Path traversal / symlinks | Workspace containment, secret-name exclusions, `.gitignore` aware inventory, symlink exclusion, current-hash recheck. | Filesystem resolution and later access are separate operations; hostile concurrent filesystem changes still need descriptor-relative OS containment. |
| Secret exposure | Token files require owner-only regular files and no symlinks; HTTP logs contain method/status only; credentials not in Git/browser storage; provider errors and command output redacted. | Redaction is heuristic. No encrypted credential store; no guarantee that malicious test code cannot read host-accessible files. |
| Command execution / network escape | No shell; exact approved commands; task worktree CWD; stripped environment, wall/output/child limits and cancellation. | An allowlisted interpreter/test framework can execute arbitrary repository code with host permissions. This is not an OS sandbox. OS network denial and mount isolation remain deployment blockers for untrusted work. |
| Unauthorized API / browser attacks | Owner bearer auth or expiring HttpOnly SameSite cookie; Host/Origin/Sec-Fetch checks; body/framing limits; CSP; no CORS; HEAD does not inherit a static handler. | Development loopback mode remains unauthenticated by explicit configuration. Use a token for real private data. Browser login UI pending. |
| Cross-project leakage | Every task/workspace/memory record references a project, guarded file APIs use registered roots. | No multi-user/project-scoped authorization or OS separation. All authenticated owner clients have owner-wide access. |
| Concurrent execution / approval race | Atomic proposal+round claim and rollback; one-way conditional approval decisions; one chat turn per conversation; at most two chat generations. | Agent/provider calls have no global resource queue; independent approved task worktrees can run concurrently. Cross-project CPU/RAM scheduling is not complete. |
| Approval bypass / cloud consent | Task provider calls retain bound approvals; cloud chat refuses transmission instead of approving itself; optional gateway is disabled by default and requires explicit enablement plus network approval even for its loopback hop. | The optional external gateway can route/fallback after opt-in; audit its separate configuration before enabling. No cloud fallback is enabled in the default product. |
| Network exposure / identity | Production entrypoint refuses wildcard/LAN/public binds; remote binding needs a Tailscale IP, token and TLS. Native client allows loopback or verified HTTPS `.ts.net`, refuses redirects/proxies/certificate overrides. | JARVIS TLS deployment and live remote identity are not verified. Token is one long-lived owner credential; rotate the file and restart to revoke it. |
| Memory poisoning | Evidence-backed promotion, provenance/staleness, explicit decisions, credential rejection. | Owner-written memory is still untrusted context. Native memory UI parity is pending. |
| Cancellation / crashes | Persisted cancellation and operation ledger; process-group stop; interrupted work not replayed; planning response after cancellation cannot publish a runnable proposal; chat content and resume cursor commit atomically. | Non-streaming legacy transports may take their timeout to return. In-flight writes already accepted by a server are not undone by disconnect. |
| Database corruption / backups | SQLite snapshot API, private files, integrity checks, new-file-only restore, reserve/quota checks and seven-snapshot refusal without deletion. | No scheduled backups, encrypted/off-device backups or tested server supervision yet. Snapshot is database-only; Git repositories/worktrees require their own approved backup policy. |
| Storage / family backups | Diagnostics walk only owned data, skip external symlinks; no cleanup or model download endpoint; Linux default reserve 200 GB, budget 75 GB. | External Ollama installations are outside measured data. Actual model/filesystem accounting awaits server inspection; no global quota enforcement for every file write yet. |
| Insecure updates | No auto-update endpoint or executable download path; pinned dependency locks, manual reviewed bundles and retained rollback snapshot. | Apple signing/notarization and update signature distribution remain unimplemented. |

Tests cover application boundary controls. They do not establish an OS sandbox, production service hardening, real remote transport, or a strong model benchmark. Read `MISSION_1_ACCEPTANCE.md` before treating the server deployment as ready.
